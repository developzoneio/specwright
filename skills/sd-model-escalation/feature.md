# sd-model-escalation - /sd:feature

The `/sd:feature` rows of the **sd-model-escalation** trigger table, and how they are decided.
Read `SKILL.md` first: the ladder, the invariants, how the override is applied, the precedence
rules and the logging contract live there and are not restated here. Why each row exists is in
`rationale.md`, which no workflow reads at runtime.

## Decision points

**The S lane has no row of its own** (ADR 0030). Its outline invocation (`/sd:feature` Phase 1S)
replaces Phase 2 and Phase 3a and has no step 0, so `ESC-FEAT-02` and `ESC-FEAT-03` cannot apply:
both read `complexity: L`, and the lane runs only for `S`. A spec that falls back to the full path
still reads `S`, so its Phase 2 and Phase 3a run at the default models. `ESC-FEAT-03b` keys on
Gate Complexity's `no-split`, which the S lane never presents, so it is unaffected too. Phase 3b
and Phase 4 rules (`ESC-FEAT-03b`, `04`, `04b`) apply on the S lane as anywhere.

**Two invocations, two lines.** `ESC-FEAT-03` and `ESC-FEAT-03b` escalate two different
invocations, so a spec sized `L` that is approved through `no-split` gets one line for each.

**Per-task decision.** `ESC-FEAT-04` / `ESC-FEAT-04b` are decided once per task, when the task is
first invoked, and that decision covers the task's re-invocations in the same pass (a scope
revert, a failing test, constitution feedback) - one line per task, not per retry. The next task
starts at the default again (invariant 3). A task regenerated by Gate Re-plan is a new task block
and is decided afresh. Several tasks can share one implementer call (a group, ADR 0031): each
task is still decided on its own and writes its own line when a rule fires, and the group's call
runs at the highest tier any of its tasks resolved to. `ESC-FEAT-04b` never meets a multi-task
group, because a `hard` task always runs alone.
